# AI个人管家项目需求分析文档 V3.0

> 当前产品基线为自动路由多会话与会话内 segment；不采用“每用户唯一永久 conversation”。本版本以模块化单体、单 LangGraph、多 PostgreSQL 作业队列为交付边界。

## 一、项目概述

AI个人管家是一款基于多 Agent 架构的个人成长管理系统。

目标是从传统问答式 AI 升级为长期陪伴用户成长的 AI 伙伴。系统提供可自动归档和恢复的多会话聊天；每个会话内部再通过上下文分段和受控长期记忆保持连续性。

第一阶段重点：以学习和职业成长场景切入，优先实现公务员备考 Agent。

## 二、产品定位与目标

产品定位：帮助用户制定目标、拆解路径、执行计划，并持续记录成长过程。

核心目标：

1. 明确用户目标
2. 生成个性化规划
3. 提供可靠资料
4. 跟踪任务执行
5. 在不增加记忆管理页面的前提下保持长期沟通连续性

## 三、产品形态

1. 第一阶段：微信小程序 + H5
2. 第二阶段：基于 uni-app 发布 iOS 和 Android 应用
3. 第三阶段：形成完整 AI 个人操作系统

前端采用 uni-app（Vue 3 + TypeScript），适合快速覆盖多端。

## 四、整体产品结构

首页就是单一聊天入口，不提供“新建对话”。用户直接表达需求，服务端在发送时自动延续、恢复或归档并建立新场景；专业 Agent 快捷入口始终可见，处理结果由大管家统一整理、追问和确认。

MVP 页面结构固定为：

1. 首页：聊天、Agent 快捷入口与多会话历史
2. 头部“计划”：独立计划、跨计划任务和执行状态
3. 头部“设置”：提醒、隐私和数据设置

学习类 Agent：

- 公考 Agent
- 雅思 Agent
- 编程学习 Agent

职业类 Agent：

- 求职 Agent
- 简历 Agent
- 职业规划 Agent

生活类 Agent：

- 健康 Agent 等

## 五、公考 Agent 需求

核心流程：

```text
用户目标输入
  → 用户信息采集
  → 资料检索
  → 学习路线规划
  → 来源审核
  → 用户确认
  → 每日任务执行
  → 阶段总结
```

功能：

1. 备考准备：考试资料、学习路线、资料推荐
2. 日常执行：任务提醒、打卡、反馈
3. 阶段总结：计划完成情况分析和调整

暂不实现：

- 成功率预测
- 能力评分模型

## 六、用户端功能

主要页面：

1. 首页：展示计划总览、管家状态和今日任务
2. 计划：按计划查看任务，也可汇总查看跨计划任务；任务打卡可直接操作
3. 聊天：与大管家沟通目标、查询资料、新建计划和调整计划
4. 我的：管理提醒、隐私和数据设置

交互约束：

- 手机号是唯一账号键，内部资源仍使用 UUID；H5 只提供手机号登录，微信小程序只提供微信登录并强制申请授权手机号。短信验证由服务端配置，默认关闭。
- 每个用户最多一个未删除的 `CURRENT` 会话。结构化流程优先延续；明显新目标在置信度至少 `0.85` 时自动归档，模糊输入必须确认；路由不可用时延续当前话题。
- 已归档会话支持查看、续聊和软删除；查看不改变状态，发送时才原子恢复。空白欢迎态不写入历史。
- 快捷入口由服务端目录驱动。首期考公为 `AVAILABLE`，雅思、求职为 `COMING_SOON`；未开放入口不得创建会话或 run。
- 专业 Agent 入口始终展示；没有未完成任务时进入临时欢迎态，用户发送第一条消息后才创建场景。
- 客户端只提交公开 `specialist_code`，不接触 `user_agent_id`。专业会话固定路由，不能在会话内静默切换领域。
- 上下文接近模型预算时，系统在后台压缩并归档当前分段、轮换 LangGraph 线程；归档过程不删除消息，也不改变聊天页面。
- AI 管家从显式资料和已通过策略的长期记忆构建用户画像；画像按偏好、习惯、稳定约束和背景组织，并可随遗忘立即失效后重建。
- 用户通过聊天执行查看、显式记住、更正、单条遗忘、忘记全部、暂停或恢复自动记忆；暂停不影响显式记住、查看和遗忘，也不回溯提取暂停期间消息。
- 用户说“清空当前上下文”时终结当前 workflow、归档当前会话并创建新的 conversation、segment 和 Checkpoint thread；旧聊天记录和显式长期记忆不受影响。
- 用户可同时拥有多个独立计划；一句话包含多个同领域子目标时，可形成一个组合计划草案并整组确认。
- 调整已有计划时，一次只能选择一个目标计划。其他计划仅用于负荷校验，不得被联动修改。
- 计划创建和调整先生成只读预览；只有带预览消息 ID、hash 和幂等键的确认接口可以创建正式业务事实，聊天文字“确认”不直接产生副作用。

## 七、MVP 范围

必须实现：

- 用户系统
- AI 管家入口
- Agent 管理
- 公考 Agent
- 资料检索
- 规划生成
- RAG 回答编号引用与来源详情
- 任务管理
- 多会话历史持久化，以及会话内部自动上下文分段与智能压缩
- 跨归档分段的受控长期记忆

MVP 只开放公考 Agent。雅思、求职和健康入口如保留在概念原型中，必须标记为“即将开放”或“概念演示”，不能进入真实的计划创建成功流程。

暂不开发：

- 健康管理
- 财务管理
- 复杂预测模型

## 八、可靠性、安全与治理需求

- 消息、单轮 run 和可续传事件必须持久化；Worker 崩溃、lease 接管和显式整轮重试不得创建计划草稿或重复业务副作用。
- Agent 输出进入业务逻辑前必须通过版本化 Schema；只有可验证事实要求形成 Claim/Citation，主观建议不制造伪引用。
- Qdrant 仅保存知识向量并强制租户过滤；长期记忆正文与 embedding 进入按用户 namespace 隔离的 LangGraph PostgresStore，业务 PostgreSQL 控制记录始终裁决权限、可见性和遗忘。
- 普通日志不得保存 Prompt、用户原文、文件/工具正文或思维链；事件默认保留 7 天，终态 run/trace 30 天，记忆审计 90 天。
- 账号删除必须可恢复地清理 Checkpointer、Store、Qdrant、对象文件和业务数据。删除期间账号保持不可登录，失败不得恢复数据可见性。
- 计划确认、任务和通知副作用必须有稳定幂等键；通知失败按 1、5、30 分钟重试，超过上限进入 `DEAD`。

## 九、本期架构非目标

- 不引入微服务、独立 API Gateway、Redis/Celery 或 MCP runtime。
- PostgreSQL 作业持续积压并影响量化 SLO 后，才重新评估 Redis/Celery；出现独立扩缩容或故障隔离需求后，才评估服务拆分。
- MCP 仅保留 tool-first 的演进接口；存在必须跨进程共享的外部工具生态时再启用 runtime。

## 十、上下文和记忆验收基线

- 单条消息最多 `1,800 Token`，约等于 1,800 个中文字符或保守估算 5,400 个英文 ASCII 字符；更长正文必须走附件和私有检索。
- Router 与提取节点正常目标/硬上限为 `2K/4K`，General 为 `4K/8K`，Planning 为 `6K/10K`，Research 为 `8K/12K`。
- 同一 segment 的多轮消息共享一个 Checkpoint thread；segment 轮换后只携带累计摘要和必要 workflow 引用，不继承旧原始消息 State。
- Checkpoint 丢失后必须能从消息、摘要、`conversation_working_states` 和 `workflow_sessions` 重建。
- 长期记忆检索最多语义召回 30 条，经控制面校验后只注入 4 条、600 Token。
- 遗忘事务提交后记忆立即不可检索；Store 删除失败只能形成待清理孤儿，不能造成记忆复活。
