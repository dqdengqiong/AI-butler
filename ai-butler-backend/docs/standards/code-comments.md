# 代码注释规范

## 目标与原则

- 代码 MUST 具有与业务复杂度相称的较为详细注释。评审者应能通过命名、类型和注释理解设计原因、适用边界、关键副作用与失败方式，而不必完整推演实现。
- 注释重点解释“为什么这样做”“必须保持什么约束”以及“修改时容易破坏什么”，不得逐行翻译代码。
- 注释是实现的一部分。修改行为、参数、返回值、异常、状态或约束时，MUST 同步更新相关注释；失真的注释按缺陷处理。
- 注释和文档字符串默认使用简体中文；代码标识符、协议字段、错误码和无法准确翻译的术语保留英文。

## 必须注释的内容

以下内容 MUST 提供注释或文档字符串：

1. 对外暴露的模块、类、公共函数和公共方法，说明职责、重要参数与返回值、可能抛出的领域异常以及可观察副作用。
2. 复杂领域规则、非直观算法、状态机、跨模块编排和多阶段数据转换，说明决策依据、关键步骤与不变量。
3. 事务边界、锁、并发领取、重试、超时、补偿和幂等逻辑，说明一致性目标、竞争条件及重复执行的结果。
4. 鉴权、数据隔离、隐私脱敏、Prompt Injection 防护和工具审批等安全边界，说明威胁来源以及该检查不可绕过的原因。
5. Agent 节点、Prompt 模板、模型结构化输出、checkpoint 与业务事实之间的约束，说明模型可决定和不可决定的范围。
6. 临时兼容方案、性能权衡、第三方限制和看似多余但不能删除的处理，说明背景、退出条件，并附稳定的 issue、ADR 或设计文档引用（如有）。
7. 正则表达式、位运算、复杂时间计算、单位换算以及有业务含义的常量，说明输入假设、单位、时区或取值来源。

简单赋值、直接委托、惯用控制流和已由清晰类型与命名完整表达的代码 MAY 不写行内注释。

## Python 文档字符串

- 公共模块、类、函数和方法 MUST 使用 docstring；私有函数在包含复杂规则、副作用或特殊失败语义时同样 MUST 使用 docstring。
- docstring 第一段简述职责。存在非直观契约时，继续说明参数约束、返回语义、异常、副作用、幂等性或安全要求，不强制重复类型标注已经表达的信息。
- `async` 函数涉及网络、数据库、模型或工具调用时，SHOULD 说明超时、取消、重试和事务持有范围。
- 行内注释放在被解释逻辑之前，靠近约束生效处；较长的背景说明应进入设计文档，并在代码中保留简短原因和链接。

```python
async def claim_run(run_id: UUID, worker_id: UUID) -> Run | None:
    """原子领取一个待执行任务。

    仅当 lease 已过期或任务尚未被领取时返回任务；竞争失败返回 ``None``，
    不将其视为系统异常。事务只覆盖状态检查与 lease 写入，模型调用必须在
    提交后执行，避免长时间持有行锁。重复领取不会产生新的业务副作用。
    """
```

## 禁止与维护

- MUST NOT 用注释掩盖含糊命名、过长函数或错误的抽象；应先改善代码结构，再补充必要背景。
- MUST NOT 提交大段被注释掉的旧代码、无效注释、生成过程说明或模型思维过程；历史实现由版本控制保存。
- MUST NOT 在注释中写入密钥、令牌、用户原文、生产数据、系统 Prompt、私有 URL 或其他敏感信息。
- TODO/FIXME MUST 写明可验证的后续动作，并关联负责人语义或追踪编号；涉及正确性、安全或验收的缺口不得仅以 TODO 延后。
- 代码评审 MUST 检查新增或修改的复杂逻辑是否满足本规范，并检查相邻注释是否仍与实现一致。
