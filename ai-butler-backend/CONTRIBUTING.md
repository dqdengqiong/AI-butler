# 贡献指南

## 工作流

- 默认分支为 `main`，功能开发使用短生命周期分支。
- 提交信息 MUST 遵循 Conventional Commits：`type(scope): description`。
- 常用类型为 `feat`、`fix`、`docs`、`test`、`refactor`、`chore`。
- 一个提交 SHOULD 只表达一个可独立审查的意图。

## 合并门槛

变更必须满足：

1. 需求或问题描述清晰，影响范围与风险已说明。
2. 代码、迁移、OpenAPI 和文档保持一致。
3. 格式、lint、严格类型检查、测试和密钥扫描通过。
4. 新增或修改行为有正常、失败和权限边界测试。
5. 日志不包含密钥、令牌、手机号、用户原文或系统 Prompt。
6. AI 参与的变更说明使用的工具、人工复核点和未验证项。
7. 公共接口与复杂逻辑具有符合 `docs/standards/code-comments.md` 的注释，且相邻既有注释与实现一致。

## 跨仓库变更

后端是 API 契约唯一来源。先更新并发布 OpenAPI，再更新前端生成客户端；两个变更记录必须互相引用。破坏性变更必须使用新的 API 版本。

## Definition of Done

- 验收标准可重复验证。
- 数据库变更具有迁移和前滚补救说明。
- 副作用具备权限校验、审批边界和幂等保证。
- 新配置进入 `.env.example`，真实值不进入仓库。
- 用户可见行为、运维行为或开发方式变化时同步文档。
- 新增或修改的复杂逻辑已补充设计原因、边界条件、副作用与失败语义等必要注释。
