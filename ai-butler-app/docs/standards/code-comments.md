# 代码注释规范

## 目标与原则

- 代码 MUST 具有与业务复杂度相称的较为详细注释。评审者应能通过命名、类型和注释理解设计原因、适用边界、关键副作用与失败方式，而不必完整推演实现。
- 注释重点解释“为什么这样做”“必须保持什么约束”以及“修改时容易破坏什么”，不得逐行翻译代码或模板。
- 注释是实现的一部分。修改行为、参数、返回值、状态或平台约束时，MUST 同步更新相关注释；失真的注释按缺陷处理。
- 注释和文档注释默认使用简体中文；代码标识符、协议字段、错误码和无法准确翻译的术语保留英文。

## 必须注释的内容

以下内容 MUST 提供注释或文档注释：

1. 导出的 composable、store、工具函数、核心类型和组件公开能力，说明职责、输入输出、状态所有权以及可观察副作用。
2. 复杂业务规则、非直观状态转换、缓存与乐观更新、失败回滚和跨页面协作，说明决策依据、边界条件与状态恢复方式。
3. SSE 字节流解码、半帧拼接、sequence 去重、断线续传和并发请求控制，说明协议假设、顺序保证及重复事件的处理结果。
4. 鉴权、令牌、隐私脱敏、附件处理和外部内容渲染等安全边界，说明威胁来源以及该检查不可绕过的原因。
5. H5、微信小程序等平台差异与降级路径，说明能力检测、编译分支及不支持场景下的用户体验。
6. 临时兼容方案、性能权衡、第三方限制和看似多余但不能删除的处理，说明背景、退出条件，并附稳定的 issue、设计文档或上游缺陷引用（如有）。
7. 正则表达式、复杂时间计算、单位换算、布局魔数以及有业务含义的常量，说明输入假设、单位、时区或取值来源。

简单绑定、直接委托、惯用控制流和已由清晰类型与命名完整表达的代码 MAY 不写行内注释。

## TypeScript 与 Vue 注释

- 导出的复杂函数、composable 和类型 SHOULD 使用 TSDoc/JSDoc；非直观契约必须说明参数约束、返回语义、副作用、异常或取消行为，不重复 TypeScript 已明确表达的信息。
- 组件注释应说明业务职责、受控与非受控状态、关键 Props/Emits 契约和平台限制；简单展示组件不要求罗列每个 Props。
- Vue 模板仅在权限分支、复杂状态组合、插槽协议或平台差异不直观时添加块注释；不得给每个元素添加说明。
- 行内注释放在被解释逻辑之前并靠近约束生效处；较长背景进入设计文档，代码中保留简短原因和链接。

```ts
/**
 * 合并一次 SSE 增量并返回可消费的完整事件。
 *

 * 服务端重连时可能重放最后一个 sequence，本函数会静默去重，避免消息和
 * 预览卡重复落入 store。协议错误会显式抛出，由调用方切换到可重试状态。
 */
export function appendSseChunk(chunk: string, remainder: string): ParseResult {
  // ...
}
```

## 禁止与维护

- MUST NOT 用注释掩盖含糊命名、过长函数或错误抽象；应先改善代码结构，再补充必要背景。
- MUST NOT 提交大段被注释掉的旧代码、无效注释、生成过程说明或模型思维过程；历史实现由版本控制保存。
- MUST NOT 在注释中写入令牌、用户原文、附件内容、生产数据、系统 Prompt、私有 URL 或其他敏感信息。
- TODO/FIXME MUST 写明可验证的后续动作，并关联负责人语义或追踪编号；涉及正确性、安全或验收的缺口不得仅以 TODO 延后。
- 代码评审 MUST 检查新增或修改的复杂逻辑是否满足本规范，并检查相邻注释是否仍与实现一致。
